# StreetForward 训练问题：原因分析与解决思路

本文档针对训练中出现的两类现象做**根因分析**（不限于表象），并给出可落地的解决方向。

---

## 一、现象回顾

- **损失不降**：Step 100/200/300 的 loss 约在 0.19–0.21 之间波动，无明显下降；`grad_norm` 约 1e-4～1e-3 量级。
- **频繁告警**：`RuntimeWarning: divide by zero encountered in divide`，出现在 `datasets/pointcloud_generators/lidar.py:325`，即 `uv = uv[:, :2] / z[:, None]`。

---

## 二、Divide-by-Zero 警告：根因与本质

### 2.1 表象

- 在 LiDAR 点云着色流程中，用相机内参和位姿把世界系下的点投影到图像平面时，对**所有点**做了 `uv = (K @ p_cam).xy / z`。
- 当某点的相机系深度 `z <= 0` 或 `z` 极小时，除法产生 inf/nan，触发警告。

### 2.2 代码层面的直接原因

当前逻辑（简化）如下：

```python
z = points_cam[:, 2]           # 相机系深度
valid = z > 1e-6               # 仅用“有效点”做后续 in_img 判断
if not np.any(valid):
    continue

uv = (intrinsic_np @ points_cam.T).T
uv = uv[:, :2] / z[:, None]    # 对所有点做除法，未排除 z<=0 或 z 很小
u, v = np.round(uv[:, 0]).astype(int), np.round(uv[:, 1]).astype(int)
in_img = valid & (u >= 0) & (u < W) & (v >= 0) & (v < H)
# 仅 in_img 的点会参与采样颜色
```

- **有效掩码 `valid` 只用于后面的 `in_img`**，并没有用于“是否参与除法”。
- 因此对所有点（包括 `z<=0` 或 `0 < z <= 1e-6`）都执行了 `uv = ... / z`，从而产生除零或数值爆炸，触发警告。
- 从**数据流**上，`in_img` 会筛掉这些无效点，所以**当前实现下 inf/nan 不会写入最终 pointcloud 的 colors**；问题主要是数值稳定性与日志噪音。

### 2.3 几何与数据层面的本质原因

- **相机系深度 `z`**：表示点在相机前方（z>0）还是后方/侧面（z<=0）。LiDAR 点是在**世界系**下的，变换到相机系后：
  - 在相机**背后**或**侧面**的点会有 `z <= 0`；
  - 在相机**正前方但非常近**的点可能因浮点误差或标定误差落在 `(0, 1e-6]`。
- 多相机、大场景下，每个相机只能看到一部分点，其余点在该相机下本来就是“无效投影”。当前实现没有在除法前按 `valid` 屏蔽，而是先除后筛，所以必然会在部分点上出现除零/极大值。
- **结论**：根因是“**投影有效性判断与透视除法的顺序反了**”——应先只对有效点做透视除法，或对 z 做安全处理后再除，而不是先全量除法再靠 `in_img` 掩盖。

## 三、损失不降、梯度很小：根因分析

### 3.1 梯度量级与裁剪

- 日志中 `grad_norm` 约 **0.0005～0.001**；配置中 `grad_clip_max_norm: 1.0`。
- `clip_grad_norm_` 返回的是裁剪前的总范数，说明**真实梯度总范数本身就很小**，裁剪几乎不起作用。因此“损失不降”不能归因于裁剪过猛，而是**反向传播得到的梯度就很小**。

### 3.2 梯度从何而来：整条反向链

StreetForward 的梯度路径（简化）为：

```
L2 loss → 渲染 RGB → 代理参数(proxy) → 渲染参数(means, quats, scales, opacity, colors)
         → offsets（×eta）→ GRU/MLP 偏移头 → 3D 特征 → sparse_conv / 2D 融合
```

梯度变小的可能环节：

1. **多视角平均**  
   - 损失对每个 target 视角是 `loss_i / N_target` 再 backward，多视角平均会**把梯度按视角数除**。  
   - 若 N_target 较大（如 6），单视角贡献的梯度就小，若再叠加“不同视角对同一点梯度符号相反”的抵消，总梯度更小。

2. **代理参数与“平均到点”**  
   - 梯度先到 proxy，再通过 `autograd.backward(render_tensors, grad_tensors)` 回写到渲染参数。  
   - 渲染参数是“每点一组”，梯度从整张图通过 rasterization 反传到每个点，本身就会**分散**；若可见点很多，单点得到的梯度更小。

3. **偏移量的强约束（tanh + 小上界）**  
   - 文档与代码中，offset 被严格限制：  
     `offset_pos = offset_max * tanh(...)`（如 offset_max=0.1），scale/omega/opacity/sh 同理。  
   - **tanh** 在绝对值大时梯度接近 0；在 0 附近梯度为 1。  
   - 若 MLP 输出在 0 附近（零初始化最后一层），梯度通路存在，但**偏移量的变化被物理上限制得很小**，反映到 loss 上的改进也小，看起来就像“不降”。

4. **零初始化的偏移头**  
   - 偏移头最后一层零初始化，训练初期 offset≈0，**刻意**避免大幅跳动。  
   - 副作用是：早期更新步长本来就小，若再叠加上面 1–3，整体梯度更弱，loss 曲线会有一段“平台期”。

5. **L2 损失与图像尺度**  
   - L2 对单像素的梯度是 `2(pred - gt)`，若 pred/gt 都在 [0,1]，单像素梯度 ≤2。  
   - 经过 rasterization 的 backward、多视角平均、再平均到点，传到 MLP 的梯度很容易被“平均小”。

6. **3D 特征与稀疏卷积**  
   - 特征从 sparse_conv、体素插值得到，若场景大、点云稀疏，单点特征对整图的敏感度有限，梯度也可能偏小。

### 3.3 小结：为什么“损失不降”

- **直接现象**：总梯度范数很小（1e-4～1e-3），参数更新步长小，loss 变化不明显。  
- **深层原因**：多视角平均、代理机制下的梯度分散、偏移量 tanh+小上界、零初始化偏移头、L2 的尺度与平均，**多重因素叠加**使有效梯度偏小，而不是单一 bug（如 nan 或数据全错）。  
- 若 pointcloud/gt 存在少量 nan（例如来自 lidar 除零路径未完全隔离），会进一步削弱或污染梯度，但当前实现中 `in_img` 已避免无效投影写入颜色，主要矛盾仍是**梯度链本身的“自然变小”**。

## 四、解决思路

### 4.1 Divide-by-Zero 警告（推荐优先做）

**思路**：在除法前只对“有效 z”做透视除法，或对 z 做安全处理，避免对无效点做除法。

- **方案 A（推荐）**：只对 `valid` 点做除法，无效点 uv 置 0 或跳过后续使用：
  - 先 `z_safe = np.where(z > 1e-6, z, 1e-6)`（或 `np.maximum(z, 1e-6)`），再 `uv = uv[:, :2] / z_safe[:, None]`；  
  或
  - 仅对 `valid` 索引计算 uv，其余点 uv 设为 0，后面 `in_img` 仍会筛掉。
- **方案 B**：保持现有逻辑，但对 `z` 做 clamp：`z_safe = np.clip(z, 1e-6, None)`，再除。这样不会出现 inf，但 `z<=0` 的点会得到错误的 uv；由于后面有 `in_img = valid & ...`，这些点不会被用来采样颜色，只是多算了一次无意义的除法。若希望彻底消除警告且逻辑清晰，仍推荐方案 A 或“仅对 valid 点除”。

**预期**：警告消失，逻辑更清晰；若存在极少数边界情况导致 inf/nan 进入下游，也可一并消除。

### 4.2 损失不降、梯度过小

**思路**：在不破坏训练稳定性的前提下，适度增大“有效学习信号”或放宽约束，让 loss 有更明显的下降空间。

1. **学习率与 warmup**  
   - 当前 lr=1e-3。可尝试略增（如 2e-3 或 3e-3），或加短 warmup（前几百步线性升 lr），使早期步长稍大。  
   - 若启用 lr_scheduler（如 cosine），确保 `eta_min` 不会过小，避免后期几乎不更新。

2. **梯度裁剪**  
   - 当前 `grad_clip_max_norm: 1.0` 几乎不触发。可暂时保持；若后续发现梯度偶尔爆炸，再适当调小。

3. **多视角与损失权重**  
   - 若 N_target 很大，可尝试暂时减少 target 数（如 3～4），或对 loss 做**不除以 N_target** 的版本（即对 N_target 个 loss 求和再 backward），使总梯度变大。需注意显存与过拟合风险。

4. **偏移量上界（eta / offset_max 等）**  
   - 在文档/代码中的 `offset_max`、`scale_max`、`eta_*` 等是保守上限。若训练稳定，可**小幅**提高（如 offset_max 0.1→0.15），让单步允许的几何/外观变化略大，便于 loss 更快响应。  
   - 建议先做 ablation（只调一项、看曲线），避免一次改太多。

5. **数据与初始化**  
   - 确认 pointcloud 的 RGB 无 nan/inf（例如在 dataloader 或 `convert_batch_to_streetforward_format` 后加一次 assert 或 log）。  
   - 若使用 tiny overfit 单场景单 segment，先确认该 segment 上 loss 能否明显下降；若单 segment 能降而多场景不降，再考虑数据分布或采样策略。

6. **监控与诊断**  
   - 记录并可视化：每步/每 N 步的 `grad_norm`、各模块的 grad_norm（若已有）、单视角 loss、以及（若容易加）proxy 上梯度的范数。  
   - 便于区分是“全局梯度小”还是“某几层梯度特别小”，再针对性调 lr、结构或损失权重。

### 4.3 实施顺序建议

1. **先修 lidar 除零**（方案 A 或 B），消除警告并保证数值干净。  
2. **保持当前训练配置**再跑一段（如 500～1000 step），看 loss 与 grad_norm 曲线。  
3. 若 loss 仍几乎不降，按顺序尝试：**略增 lr 或加 warmup** → **稍放宽 offset/eta 上限** → **调整 target 数量或 loss 聚合方式**，并配合上述监控做判断。

---

## 五、总结

| 问题 | 表象 | 根因 | 解决方向 |
|------|------|------|----------|
| Divide-by-zero 警告 | `uv = uv/z` 时 z 有 ≤0 或极小 | 有效掩码只用于筛 in_img，未用于“是否参与除法”；几何上存在相机背后的点 | 除法前用 valid 或 z_safe，只对有效点除或 clamp z |
| 损失不降、梯度很小 | loss≈0.2 平稳，grad_norm≈1e-3 | 多视角平均、代理分散、偏移 tanh+小上界、零初始化、L2 尺度等叠加，使有效梯度偏小 | 调 lr/warmup、适度放宽 offset/eta、调整 target 数或 loss 聚合、加强监控 |

两者相互独立：修除零不会直接让 loss 降，但能保证数据与数值稳定；损失不降需要从优化与梯度链上做上述针对性调整。
